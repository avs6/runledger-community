---
title: "Workflows"
description: "The workflow is RunLedger's top-level object: link it to a feature tag or gateway alias and every run, cost, score, budget and policy for that work is attributed to it."
---

A **workflow** names one piece of AI work, such as a support bot, a code reviewer or a
nightly summarizer. Runs are attributed to it **at ingest**, so its runs, cost, latency and
quality come from the same metering stream as the rest of RunLedger. Nothing is written by
hand and nothing has to be "executed" by RunLedger.

Each run (`agent_runs` row) carries a `workflow_id`. `workflow_runs` is a read-only SQL
view over those runs, kept for reporting tools.

## How runs find their workflow

The first match wins, always inside the run's own workspace (an id from another workspace
is ignored), and archived workflows never match:

| Order | Source | How to send it |
|---|---|---|
| 1 | Explicit reference: workflow id, its `feature_tag` or its name | SDK `@rl.workflow("…")` / `rl.withWorkflow('…')`, `run_start.workflow` / `workflow_id`, the `X-RunLedger-Workflow` header on `/ingest/v1/*` and `/v1/traces`, OTLP attributes `runledger.workflow.id` or `runledger.workflow` |
| 2 | The run's `feature_tag` | anything that already sets a feature tag (SDK context, OTLP `runledger.feature_tag`, gateway metadata) |
| 3 | The gateway alias the request used | link the workflow to a route alias |

When a workflow matches and the run has no feature tag, the run inherits the workflow's tag,
so **feature-tag budgets, chargeback and analytics see the traffic too**. A workflow's
budgets are simply `feature_tag` budgets on its tag; they are enforced wherever feature-tag
budgets are (ingest counters, `/budgets/check`, the gateway preflight).

Creating a workflow, changing its tag or alias, or restoring it links existing runs that
have no workflow yet (`linked_runs` in the response). Explicit attribution is never
overwritten.

Agents are attributed the same way: `agent_name` / `agent_id` on `run_start`, the SDK's
`agent=` argument, or the OTLP attributes `runledger.agent`, `runledger.agent.id` and
`gen_ai.agent.name`.

## Send traffic

<CodeGroup>
```python Python SDK
from runledger_sdk import RunLedger

rl = RunLedger.from_env()

@rl.workflow("support-triage", agent="triage-bot")
def triage(ticket):
    ...  # model calls in here are attributed to the run; failures are recorded
```

```ts TypeScript SDK
import { RunLedger } from '@runledger/sdk'

const rl = RunLedger.fromEnv()
await rl.withWorkflow('support-triage', async (task) => {
  // model calls in here are attributed to the run
}, { agentName: 'triage-bot' })
```

```bash Ingest API
curl -X POST http://localhost:8201/ingest/v1/batch \
  -H "Authorization: Bearer $RUNLEDGER_API_KEY" \
  -H "X-RunLedger-Workflow: support-triage" \
  -d @events.json
```

```bash OpenTelemetry
# per span or resource:  runledger.workflow = "support-triage"
# per service, on the exporter:
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer $RUNLEDGER_API_KEY,X-RunLedger-Workflow=support-triage"
```
</CodeGroup>

`@rl.workflow` works on sync and async functions. With `agent_id=…` it first calls
`GET /agents/{id}/envelope` and raises `RunLedgerBudgetExceededError` when the agent's
monthly budget envelope is spent or the agent is paused or retired.

## API

| Method | Path | What it does |
|---|---|---|
| `POST` | `/workflows` | Create. `name`, optional `feature_tag` (unique among live workflows; 409 otherwise), `gateway_alias` (must be an existing route; 422 otherwise), `owner`, `description` |
| `GET` | `/workflows` | List with stats for the window: `status`, `q`, `feature_tag`, `api_key_id`, `days`, `sort`, `dir`, `limit`, `offset` (total in `X-Total-Count`) |
| `GET` | `/workflows/{id}` | One workflow with stats |
| `PUT` | `/workflows/{id}` | Edit, re-link, archive (`status: "archived"`) or restore (`status: "active"`) |
| `DELETE` | `/workflows/{id}` | Archive. Workflows aren't hard-deleted: runs reference them, and an archived workflow stops matching new traffic |
| `GET` | `/workflows/{id}/overview` | The Workflow page: health, budgets, evals, policies, agents |
| `GET` | `/workflows/{id}/runs` | Runs attributed to it: `status`, `agent_id`, `api_key_id`, `days`, paging |
| `GET` | `/workflows/{id}/cost` | Cost by step and by model for the window |

### Health card

`/overview` returns `health` for the window (`days`, default 30):

- `cost_per_success`: total cost divided by succeeded runs
- `p50_latency_ms`, `p95_latency_ms`: run duration percentiles
- `success_rate`, `runs`, `succeeded`, `failed`
- `avg_eval_score` and `eval_score_delta` (second half of the window minus the first),
  from `score_events` on the workflow's runs
- `trend`: per-day runs, cost and average score

### Cost by step

A step is a span name inside the workflow's runs. Its cost is the sum of the provider calls
made under it, so `steps_cost` equals the runs' `total_cost` once metering has priced every
call. There is no separate step ledger to drift.

## In the app

- **Workflows** is the landing page and the first item in the navigation. It lists
  workflows with runs, success rate, cost per success, spend and p95 latency, with search,
  a status filter and a stats window kept in the URL. Create, edit, archive and restore from
  the list or the detail page.
- **Guided setup** (`/workflows/new`) walks a first workflow through three steps: name it,
  copy one snippet for the way the team sends traffic, then wait for the first attributed
  run.
- The **workflow page** shows the health card, the runs table (each row opens the run),
  cost by step and by model, the feature-tag budgets with their spend, evaluator scores,
  the controls that apply (routes on the linked alias, routing policy, guardrails, tool
  policies) and the agents that ran in it.

## Migrating from workflow runs and steps

Before the `workflows_spine` migration, runs were posted by hand to
`POST /workflows/{id}/runs` and `/workflows/runs/{id}/steps` with their own cost fields.
Those endpoints are gone. The migration drops the record-only `workflow_runs` and
`workflow_steps` tables (they were never connected to real traffic), links workflows to the
`feature_tag` in their `config` when there was one, and back-fills `agent_runs.workflow_id`
from feature tags. To keep reporting a workflow, set its feature tag and send traffic with
that tag.
