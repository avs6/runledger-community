The Security console is the governance home for enterprise auth posture and request-edge network controls.

## What lives here

- **Secrets** - every stored credential with its age, last rotation, the key that encrypts it, a
  **Rotate** action, **Re-wrap** (re-encrypt with the current master key) and its own audit timeline
- **Sign-in providers** - OIDC, OAuth2 and LDAP providers with full create, edit and delete
- **Security posture** - required metadata fields and their enforcement mode (`reject` is enforced by the gateway). Residency, callback, branding and OIDC-session settings were removed: they were stored but never enforced.
- **OIDC providers** - create, edit, activate, deactivate, and delete issuer configurations for gateway auth
- **IP ACL rules** - create, edit, simulate, and delete allow or deny rules for workspace, API-key or access-group scope (global rules, which apply to every workspace, are platform-admin only)

## Secrets: write-only, encrypted, rotated

Every credential RunLedger stores is encrypted at rest with `core/secrets.py` (Fernet with
`SECRETS_MASTER_KEY`, or AWS KMS envelope encryption with `SECRETS_KMS_KEY_ID`):

| Secret | Where it is set |
|---|---|
| OIDC / OAuth2 client secret, LDAP bind password | Security → sign-in providers |
| Search-provider credentials (`auth_config`) | Tool registry → search providers |
| Pass-through `auth_config` and secret headers | Gateway → pass-through endpoints |
| Notification webhook / Slack URL | Budgets → notifications |
| Evaluator provider key (`config.api_key`) | Evaluation → evaluators |
| Kafka, backup, GitHub tokens and ledger keys | Integrations, backups, prompts, ledger |

Secrets are **write-only** in the API and UI. Responses show `••••••••` (webhook URLs show only the
scheme and host); sending the mask back on an update keeps the stored value, and a form field shows a
**Replace** button instead of the value. A decryption failure is an error; RunLedger never falls back to
using ciphertext as a key.

The **Secrets** card lists each secret with an age badge (fresh, aging after 60 days, stale after 90),
its last rotation and who did it, and the key id that wraps it.

- **Rotate** replaces the value (`POST /security/secrets/{id}/rotate` with `value`, or `values` by key for
  JSON configs). It is recorded as `secret.rotated`.
- **Re-wrap** re-encrypts with the current primary key after you add a new `SECRETS_MASTER_KEY`
  (`POST /security/secrets/{id}/rewrap`, or `POST /security/secrets/rewrap` for the workspace).
- **Timeline** shows `secret.created`, `secret.rotated`, `secret.rewrapped` and `secret.deleted` events
  (`GET /audit/events?target_type=secret&target_id={id}`).

The inventory is maintained by the database session itself: any code path that changes a secret updates
it, so it can't drift. Writing back an unchanged value is not counted as a rotation.

## LDAP

A service bind DN needs a bind password (422 otherwise), and sign-ins reject empty passwords, because an
empty password is an unauthenticated bind. Directory calls run in a worker thread so they never block the
API's event loop.

## Operator workflow

1. Set `SECRETS_MASTER_KEY` before storing any secret in production.
2. Set the workspace security posture.
3. Register sign-in providers (OIDC, OAuth2, LDAP).
4. Add IP ACL rules for sensitive traffic paths, and run the simulator before saving broader deny rules.
5. Review the Secrets card monthly and rotate anything stale.

## How IP ACLs are enforced

The gateway applies IP ACLs to every request, including cache hits and OIDC-authenticated callers.

- **Which rules apply**: global rules, this workspace's rules, rules for the calling API key, and rules
  for access groups the caller belongs to. The caller is the API key's owner, or the user named in
  `X-RunLedger-End-User-Id` (user id or email) when the key has no owner.
- **Decision**: the first matching rule by priority (lowest number first) decides. If no rule matches,
  the request is refused only when an allow rule applies (allow-list mode); a set of deny rules blocks
  just those ranges.
- **Client address**: the gateway uses the connection's peer address. It believes `X-Forwarded-For` only
  when the peer is a trusted proxy listed in `RUNLEDGER_GATEWAY_TRUSTED_PROXIES` (comma-separated CIDRs;
  `GATEWAY_TRUSTED_PROXIES` in `.env`, `gatewayTrustedProxies` in Helm), and then takes the right-most
  address that isn't a trusted proxy, so a client can't claim an allow-listed IP.
- **Validation**: CIDRs are checked when a rule is saved (422 if invalid), and API-key and access-group
  rules must name a key or group in this workspace.
- **Legacy team rules**: the old team scope was replaced by access groups. Migration 095 mapped team
  rules to the access group with the same name; any that couldn't be mapped never match and are flagged
  on the Security page for reassignment or deletion.

## Defence in depth

- Tenant tables carry Postgres row-level security keyed on the caller's org (and workspace for workload
  keys). See [configuration](/deployment/configuration#database-role-and-row-level-security) for the
  database role it needs.
- gateway-rs and the MCP gateway each use their own internal secret (`GATEWAY_INTERNAL_TOKEN`,
  `MCP_INTERNAL_TOKEN`) instead of the shared admin secret, and Caddy refuses `/gateway/runtime/internal/*`.

Verify everything on this page end to end with `python scripts/run_demo.py verify-secrets`.

## Notes

- The legacy team scope is gone; use access groups to scope IP ACLs to a set of users.
- Security is a managed admin surface, so completion is based on full lifecycle controls rather than read-only observability.
