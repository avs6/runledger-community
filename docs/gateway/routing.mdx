Each model alias can have multiple routes. When a request arrives, RunLedger selects a route by policy, tag filters, region preference, and health state, then falls back if the chosen provider fails.

## Fallback behavior

Routes carry a `priority` where lower numbers are tried first. On a transient provider failure the gateway retries and then moves to the next eligible route. That means provider failures are absorbed by the fallback chain and hidden from clients unless every eligible route fails.

Transient failures (429, 5xx, timeouts, connection errors) are retried `retry_count` times, waiting the
provider's `Retry-After` or an exponential backoff from 250 ms (capped at 5 s) between attempts, and then fall
through to plain fallbacks (`fallback_config.aliases`, request `fallback_aliases`). Non-transient failures
(400, 403, 413…) aren't retried and skip plain fallbacks, because another route won't fix a bad request.
They only fall through to an **error-triggered fallback** whose `on` list matches the error:

```json
{ "fallback_config": { "fallbacks": [ { "alias": "long-context", "on": ["context_window"] }, { "alias": "lenient", "on": ["content_policy"] } ] } }
```

`context_window` matches a 400/413 that mentions the context length; `content_policy` matches a 400/403
that mentions a content filter or policy. A rule may also override `messages`, `temperature`,
`max_tokens` and other request fields for its step. When nothing matches, the client gets the provider's
own status (for example 400 or 413) with `upstream_status`, `upstream_body` and `error_triggers`, not a
502; a 429 is returned as 429, and other exhausted chains as 502.

## Timeouts

Each route has a `timeout_ms` (1–300 s), and `config.completion_timeout_ms` / `config.stream_timeout_ms`
can set separate limits for non-streamed and streamed calls. A caller can override them for one request
with headers (milliseconds, 1,000–300,000):

| Header | Applies to |
|---|---|
| `X-RunLedger-Timeout-Ms` | non-streamed calls (when no completion timeout is given) |
| `X-RunLedger-Completion-Timeout-Ms` | non-streamed calls |
| `X-RunLedger-Stream-Timeout-Ms` | streamed calls |

A fallback rule may set its own `completion_timeout_ms`. Overrides apply to that request only and are never
written to the route. A provider that times out returns **504** to the gateway (a transient failure, so
retries and plain fallbacks apply); a provider error returns its own status and body.

## Mirror (shadow) traffic

Set `mirror_config` on a route to send a sample of its successful non-streamed requests to a second alias
for comparison:

```json
{ "mirror_config": { "alias": "candidate-model", "sample_pct": 0.1 } }
```

The gateway samples the request and fires the shadow call in the background after it has replied, so
users never wait for the shadow model. The shadow call reuses the prompt that already passed pre-call
guardrails, is redacted again if the shadow route has `pii_redaction_enabled`, and is recorded as a
priced run flagged `shadow` (`source_type: gateway-shadow`), attributed to the same workflow and counted
against budgets, since it is real spend. The request log shows it as `mirror:<alias>` with a
`shadow_compare:<similarity>` decision.

## Routing strategies

Routing strategies are configurable through both the API and the Gateway UI.

| Policy | Purpose |
|---|---|
| `manual` | Priority-order routing |
| `cost_optimized` | Cheapest route above a quality floor |
| `latency_optimized` | Lowest recent p95 latency |
| `quality_optimized` | Highest average quality score |
| `weighted` | Weighted traffic split |
| `canary` | Gradual rollout to one route |
| `ab_test` | Experiment split with significance analysis |
| `budget_aware` | Fallback alias when budget threshold is hit |
| `complexity_based` | Branch by request complexity |
| `outcome_optimized` | Lowest cost per successful outcome |

## Tag-based routing and exclusion flows

Routes support both `required_tags` and `excluded_tags`. This allows:

- **Tier routing** such as `tier:cheap`, `tier:mid`, and `tier:frontier`
- **Provider exclusion** such as excluding `provider:openai` or `provider:anthropic`
- **Safety or residency slices** such as excluding `region:eu` or `data:restricted`

Routing groups can also contribute default tags for untagged traffic, which makes the tier and provider exclusion flow work even when callers do not pass custom headers.

## Policy and group rules

- A route in a routing group always has the group's alias. Changing the alias of a grouped route returns
  **400** unless the same request moves it out of the group; renaming a group that still has routes
  returns **409**.
- Every route a policy names (`weights` keys, `canary_route_id`, `variants[].route_id`, or the route passed
  to promote) must be in the workspace and serve the policy's alias.
- `policy_type` must be a known strategy on create and on update.

Use **Test request** on the Routes tab (`POST /gateway/routes/preview`) to see which route an alias resolves
to, with estimated cost and recent latency, and review the diff that every route edit shows before it saves.
See [Gateway administration](/gateway/administration).

## A/B testing validity

Production A/B testing uses:

- per-variant request counts
- success and error rates
- significance testing with a configurable `significance_threshold`
- minimum sample enforcement before a winner can be promoted

Winner promotion for A/B tests is blocked until significance and sample requirements are met.
