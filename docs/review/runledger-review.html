Technical due diligence · RunLedger Community

A wide control plane whose enforcement path hasn't caught up with its surface area

RunLedger has an unusually broad product surface for a single-maintainer codebase: about 100 UI routes, 636 API endpoints, a Rust data plane and nine optimization sidecars. The observability and gateway core is real and works on live traffic. But several headline promises (budget enforcement, tool governance, workflow-centric attribution, intelligent routing) are advisory, disconnected or broken in the runtime path. A large share of recent engineering went into cross-linking "posture" cards instead of deepening those paths.

Remediation status (refreshed 2026-11-22, master 5639c29): Organization & Access (22 of 23 findings) and Ingestion & Integrations (27 of 27) are fixed and merged, along with 45 dashboard endpoints that returned 500. Billing & Chargeback (13 findings) is fixed on branch docs/review-status-refresh: chargeback rules applied to cost centers, locked and frozen period close with reopen, per-workspace signing keys, one billable-cost definition. That closes the cross-tenant account takeover (A-01/A-02), whole-database backups by org admins (P-02/I-03), unauthenticated and cross-tenant ingest (I-01/I-02), OTLP noise runs (#6), and gateway budget enforcement (#1). Still open from the top 12: model budgets (#2), intelligent routing (#3), no workflow dimension on runs (#4), tool policies at the gateway (#5), posture sprawl (#7), overlapping budget concepts (#10) and most pagination (#12). Across the feature audit, 85 of 214 findings are resolved — see Status overview.
Pass 2 is available: code-level deep dive covering the gateway subsystems, budget enforcement and governance, with file:line evidence. A fourth pass, the parallel feature audit (213 findings, 10 new critical, including cross-tenant account takeover), audits every major feature's backend, frontend and cohesion. A third pass, the page-by-page UI walkthrough, checks every nav item, tab, filter and paginator against the code. Pass 2 adds two critical security findings (guardrail-sandbox RCE; secret exfiltration and SSRF via route config), confirms in production that streamed gateway traffic is never metered Resolved: streams are now metered (G-03), and corrects several statements in this report (marked "corrected in pass 2").

Scope: repository at branch feat/claude-code-log-runs (master d32883b) plus the live home-lab deployment at 192.168.1.72 (33 containers, read-only inspection). Reviewer stance: technical VC / software architect.

Verdict

What's genuinely strong
  • Ingests real traffic: 275,912 runs and about 2M spans on the home lab via OTLP, the gateway and the SDK.
  • Credible OpenAI-compatible gateway with routing groups, fallback triggers, canary/rollout/rollback policies, exact and semantic cache, and pre/post guardrails that are actually evaluated in the hot path.
  • Serious breadth in FinOps primitives: billing periods, reconciliation, signed exports, chargeback rules, shared-cost allocation, adjustments, HMAC-signed ledger snapshots.
  • Enterprise table stakes are present: OIDC, OAuth2, LDAP, IP ACLs, audit log, access groups, retention model, HA/backup docs, Helm.
  • Disciplined backend hygiene: ruff, mypy and pytest in CI, 637 API tests, 78 Alembic migrations, typed Pydantic schemas throughout.
What would stop a diligence process
  • Budgets aren't enforced inline. check_budgets() is never called from the gateway preflight, even though the docs say "Inline (gateway): blocking, enforced before the provider call". Resolved: gateway preflight enforces scoped budgets (block → 429, throttle, downgrade)
  • Model budgets are dead. Their spend counter (incr_model_budget_spend) and check (check_model_budgets) are never called.
  • Tool policies and approvals are advisory. They only apply if a client voluntarily calls /policies/check or an MCP tool.
  • Intelligent routing is broken in production. The API calls gateway-rs/classify, which returns 404, and silently fails open after a timeout of up to 25 s. Resolved: built-in classifier
  • "Workflow" isn't a dimension on runs. agent_runs has no workflow_id. Workflows are a separate registry with manually posted run records and their own cost columns.
  • Most production runs are noise. About 92% of production runs are Codex app spans with $0 cost and no model calls. The FinOps numbers aren't trustworthy on this dataset. Partly resolved: new non-AI traces are dropped by OTLP gating; existing noise rows remain

Stage call: late alpha / early beta on the control-plane side; early alpha on enforcement. The product is observably complete but not yet enforceably complete. The fastest path to a defensible product is to stop widening, collapse the posture layer, and make five runtime paths real: budgets, tool policy, approvals, workflow attribution and routing.

Architecture: request path reality vs. the diagram

The docs describe a Rust data plane with the Python API "out of band". In code, every control decision goes through the Python control plane over HTTP, authenticated with the shared x-admin-secret. For OpenAI-compatible providers Rust makes the upstream call itself; Azure, Bedrock, Vertex and Gemini are also proxied through Python. See pass 2 lifecycle.

Latency claim

The login page advertises "<5ms" gateway overhead. With 4–5 synchronous internal HTTP hops, a Postgres SUM() over gateway_requests per request for cost caps, and optional sidecar calls, that claim can't hold. No benchmark in scripts/bench asserts it.

Blast radius

If the Python API is slow or down, the "data plane" is down too: readiness probes /health/live on the control plane. The gateway can't serve from a cached snapshot, although /runtime/internal/snapshot already exists.

Coverage

The Rust plane implements only /gateway/chat/completions. Embeddings, Responses API, Anthropic Messages, images, audio and batch aren't routed. Bedrock streams are fully buffered before being returned.

Other architectural observations

  • Monolithic routers. analytics.py (634 KB, about 8,500+ lines) mixes core analytics, economics, engineering, scorecards and 68 posture endpoints. org.py is 60 KB, runs.py 62 KB. These are merge-conflict magnets and untestable as units.
  • Tenant isolation by convention. 1,633 explicit workspace_id == filters across routers and no Postgres RLS. One missing filter is a cross-tenant leak. Consider RLS with SET app.workspace_id per request as defense in depth.
  • Sidecar sprawl. 26 compose services. The home lab runs about 33 RunLedger containers (Letta, Kùzu, Qdrant, memory-db, Redpanda, MinIO…) for a product with 14 users. A "core" profile of api + web + worker + postgres + redis should be the default story. Partly resolved: Redpanda moved to an opt-in streaming profile; other sidecars unchanged
  • Dead and legacy code still shipped. routers/projects.py isn't mounted but its model and schema remain. team_models is still referenced by services/gateway.py and gateway_controls.py. gateway_legacy is mounted. 27 page routes are redirect stubs. Partly resolved: projects router removed and team_models no longer referenced by the gateway; legacy models remain

Posture-card sprawl

The single most important product-engineering observation. The project's own TODO_ITEMS/FEATURE-STATUS.md tracks a "cohesion matrix" (every feature × every other feature) and closes cells by adding a posture endpoint + colored card, for example "WU-016 adds Runtime Scope & Evidence posture card (cyan theme)… 5 cells closed". Cohesion is being measured by links between screens, not by shared runtime behavior.
68
posture endpoints in analytics.py (/overview-gateway-posture, /tags-runtime-posture, /vector-store-detail-evidence-posture…)
56 pages
render one or more posture cards. The Gateway page renders 23.
83
numbered examples (100–178) whose only purpose is to GET a posture endpoint

Why it matters

  • Cost. Each card is one more round trip and about 8–12 COUNT(*) queries per page load. On a 275k-run workspace that's real Postgres load for "context" tiles.
  • Cognitive load. Every page ends in the same grid of violet / amber / emerald / cyan / rose summary cards, so the page's primary job gets buried and screens look alike.
  • False completion signal. A cell going from PARTIAL to STRONG because a card links to Budgets doesn't mean budgets constrain that feature. Finding #1 is proof: Budgets is "STRONG" across the board yet unenforced.
  • Violates the repo's own AGENTS.md. "Reject or refactor changes that introduce decorative configuration… or UI surfaces with no real enforcement path."

Recommended replacement

One relationship service: GET /context?entity=workflow&id=… returns the related budgets, routes, policies, keys, recent runs and violations as typed edges. Add one reusable <RelatedPanel> (right-hand drawer), lazy-loaded on open. Delete the 68 endpoints, 121 fetchers and 83 examples. Expect about 10–15k LOC removed and a measurable drop in page load time.

Investor lens

Positioning

The market is crowded at each layer: observability (Langfuse, LangSmith, Helicone, Arize/Phoenix), gateways (LiteLLM, Portkey, Kong AI, Cloudflare AI Gateway), FinOps (Vantage, CloudZero adding AI). RunLedger's credible wedge is self-hosted, workflow-level cost + governance enforcement in one control plane: "the ledger that can say no". That wedge depends on exactly the paths that are advisory today. Fix those and the story is differentiated. Without them it's a very broad dashboard.

Moat candidates

  • Signed, tamper-evident AI spend ledger (needs a hash chain and external anchoring).
  • Workflow-level unit economics (cost per successful outcome) joined to eval quality.
  • Closed improvement loop: opportunity → simulate → apply routing policy → measure. The pieces exist but aren't connected.

Execution risk

  • Breadth over depth. About 100 screens with enforcement gaps signals a roadmap optimized for coverage metrics (cohesion cells) rather than customer-visible guarantees.
  • The AI-assisted development pattern is visible: posture cards, numbered examples, matrices. High throughput needs strong architectural guardrails; AGENTS.md has them, but they aren't enforced in review.
  • Operational footprint (26+ services) raises the self-hosting barrier for the community edition.

G-18MediumIP ACL is spoofable and crashes for OIDC callers Resolved: trusted-proxy XFF, OIDC-safe, access groups instead of team; also fixed deny-only rule sets, unvalidated CIDRs and org admins creating cross-tenant global rules

In preflight, evaluate_ip_acl(..., api_key_id=api_key.id, ...) (gateway_runtime.py:211) dereferences api_key, which is None for OIDC-authenticated callers, so OIDC callers sending XFF get a 500. Required-metadata enforcement supports both modes: warn (appended to decision_reason as metadata_warn:) and reject (settings.required_metadata_mode == "reject" raises, services/security.py:786; exposed on the Security page). Note it's evaluated after the IP ACL but before the cache, so it's one of the few controls cache hits don't skip. Tags are merged from body metadata and the X-RunLedger-Tags header, then resolved. That's reasonable.

Exact cache & semantic cache

G-05HighCache hits bypass guardrails and controls

The exact-cache check (gateway_runtime.py:231-267) and semantic-cache check (269-314) both return before pre-call guardrails (349), cost caps and RPM. A prompt that a guardrail added later would block is still answered from cache. A rate-limited end user keeps getting answers, and a guardrail-modify (PII redaction) never runs on cached paths. Cache hits also skip run recording: they create a GatewayRequest row only, so cache-hit traffic is invisible in Runs and in savings attribution by workflow. Resolved: guardrails now run first; cached prompts a new guardrail blocks get 451

Fix: order = auth → ACL → guardrails(pre) → rate/budget → cache → route. Record a zero-cost run with cache_hit=true so savings are attributable.
G-06HighSemantic cache leaks responses across users in a workspace

_scope() sets security_scope: "" and knowledge_version: "" with a comment "Placeholders until … wired (P5+)" (services/semantic_cache.py:44-52). Any two callers in the same workspace with the same model and system prompt share answers at ≥0.95 cosine similarity. User A's answer containing their account data can be served to user B. The exact cache has the same problem: workspace-scoped, not key- or user-scoped. Resolved: security_scope is the caller and parameters

Fix: include api_key_id (default) or end_user_id in the scope. Make "shared" an explicit per-route opt-in. Never semantic-cache responses containing tool calls.
G-07HighExact cache key ignores request parameters

make_cache_key(model, messages) hashes only model + messages (services/gateway.py:111). Requests with different tools, tool_choice, response_format (JSON-schema vs text), temperature, seed or max_tokens collide. A caller asking for JSON can receive a cached prose answer, and an agent offered different tools can receive a tool call for a tool it doesn't have. Caching is on by default (body.get("cache")…unwrap_or(true), main.rs:586-589). Resolved: params included

Fix: hash the canonical provider-bound body (minus stream and user). Skip caching when temperature>0 unless explicitly requested. Default cache=false.
G-19MediumLookup and store use different keys

Lookup hashes the original messages (233); finalize stores under prepared_messages, which are post-compiler and post-guardrail-modify (657). With the context compiler or a modify guardrail enabled, the exact cache never hits, yet the UI reports it as enabled. Resolved: same key for lookup and store

Context compiler & intelligent router

G-09HighRaw prompts leave the trust boundary before guardrails Resolved: guardrails and PII redaction run first; redaction covers non-streamed calls

The compiler (316-328) and router (333-347) run before pre-call guardrails (349), so unredacted content (PII, secrets) is sent to two sidecars, and to whatever model the router uses. G-04HighIntelligent routing is a silent no-op with a 25-second tax Resolved: built-in classifier in the API; external classifier optional

G-08HighModify-mode rewrites the wrong messages

pre_texts includes only messages with truthy content (359), but the rewrite loop indexes messages by position (376-381). Fallback, retries, error semantics

G-11HighError-triggered fallbacks can't fire Resolved: trigger-matched fallbacks run, provider status returned, Retry-After backoff; route form edits the rules

Policy fallbacks carry required_error_triggers such as content_policy or context_window. In Rust, a step with required triggers is skipped unless a previous failure produced that trigger (main.rs:524-531). But providers return those errors as 400/413, which are non-transient, and the loop returns 502 immediately on any non-transient failure (622-632). The trigger is classified and then thrown away, so the "fallback on content filter / context overflow" feature never fires.

Fix: on non-transient failure, continue to the next step whose triggers match; return only when none match. Return the provider's status code (400/413) instead of 502.
  • Retries with no backoff or jitter (533-535): a 429 is retried immediately up to retry_count times, which makes rate limiting worse. Retry-After is ignored.
  • Cooldown is set on transient failures via /internal/route-result, with one synchronous DB commit per attempt (gateway_runtime.py:758-778). Even success commits a row update on every request.
  • Upstream error bodies are echoed to clients verbatim (upstream_body), which can leak provider account details.

Streaming & finalize

G-03CriticalStreamed requests are not metered, recorded or guarded

On ProviderSuccess::Stream, Rust emits one gateway.request.completed event (no token counts) and returns the stream (main.rs:536-560). It never calls finalize, so streaming requests get no AgentRun, no Span, no ProviderCall, no cost, no post-call guardrails, no cache store. The only trace is the event, and that fails too: uuid_like() returns "gw_" + hex (1168-1170), which isn't a UUID, so the API's event endpoint returns 400. Production gateway-rs logs show 12 "runtime event emit failed … 400 Bad Request" since the last restart, and the same 400 hits every rejected (all-routes-failed) request. Streaming is the default mode for coding agents and chat UIs, so the gateway's FinOps view systematically misses its largest traffic class.

Fix: tee the SSE stream in Rust, parse the final usage chunk (send stream_options.include_usage=true upstream), and call finalize asynchronously after the stream ends with accumulated content. Use real UUIDv4 request IDs. Add a contract test that posts a Rust-shaped event to the API.

B-01CriticalNo inline enforcement

B-02HighThe counter feed skips gateway traffic

Gateway finalize writes ProviderCalls with cost_usd already computed (gateway_runtime.py:124-141), so enrichment never sees them. B-03 · B-04HighScope handling is inconsistent between increment and sync

Increment: _matching_budgets(budgets, end_user_id=…, feature_tag=…). api_key, access_group, app and provider_profile are never passed, so those budgets never accrue (metering.py:144-148). Sync: filters only for end_user and api_key. For every other scope it sums all workspace spend, with a comment "feature_tag is on agent_runs … skip for now" (workers/budgets.py:238-259). A $20 feature_tag budget is therefore reset nightly to, say, the $4,000 workspace total and shows as 20,000% consumed. Through /policies/check it then blocks or downgrades every request for that feature. Access-group budgets, which the docs call "first-class budget scopes", are wrong in both directions. Resolved: increment path fixed for all scopes; nightly sync computes each scope's own spend (I-08)

B-05HighCounters aren't durable

Redis runs with --maxmemory 256mb --maxmemory-policy allkeys-lru --appendonly ${…:-no} (docker-compose.yml:55). Under memory pressure from response caches, rate-limit keys or Celery, LRU may evict rl:budget:*:spend:*, resetting spend to 0 until the next daily sync. A Redis restart without AOF does the same.

Fix: use Postgres as the source of truth (a budget_spend table updated transactionally in finalize/ingest), Redis as a write-through cache with volatile-lru, and keep budget keys without TTL eviction.
B-07 · B-08MediumTime attribution and stalls

Counters use datetime.now() at enrichment time (services/budgets.py:72), so a call made at 23:59 and enriched at 00:01 lands in the next day, and backfilled pricing dumps historic spend into today. Enrichment orders by created_at and LIMIT 500; unpriced calls are skipped but stay NULL, so once 500 unpriced calls exist, every run re-selects the same 500 and enrichment stops for all newer calls.

B-09MediumRunaway protection doesn't protect

Every 5 minutes the worker finds runs with status='running' for >2 minutes with >20 calls or a >100k-token call and sets status='cancelled' (workers/budgets.py:81-120). Gateway and OTLP runs are created as succeeded, so they never qualify. Nothing in the gateway checks run status, so a "cancelled" run keeps spending. It's notification-only behavior presented as a kill switch.

Governance & security

Custom guardrail sandbox

S-01CriticalRemote code execution in the API process

execute_custom_logic compiles and exec()s user-supplied rule.logic (services/guardrails.py:164-166). Its only protection is a regex denylist (100-129) for words like import, __class__, getattr, os.. The sandbox globals expose the real re module (97). Module objects carry references back to builtins and other modules, and string-built attribute names defeat word-boundary regexes. Denylist sandboxes of this kind are a well-known, repeatedly broken pattern. Also: Resolved: replaced by services/guardrail_logic.py (AST interpreter, step/time/size limits)

  • timeout_ms is accepted but never enforced, so while True: pass blocks the async event loop and stalls every request on that worker.
  • POST /guardrails depends only on WorkspaceDep (any valid API key, including SDK and ingest keys embedded in agents), while update requires workspace admin (routers/guardrails.py:123-131 vs 245-253). Resolved: POST /guardrails requires workspace admin
  • Exceptions fail open (return allow), so a broken rule silently disables itself.

Impact: code runs with the API's environment (DATABASE_URL, SECRET_KEY, ADMIN_SECRET, provider keys), so it's a cross-tenant compromise.

Fix (immediately): disable custom/template logic execution behind a feature flag defaulting off; require workspace admin on create. Then: replace with a non-Turing-complete policy language (CEL, JSONLogic, Rego/OPA) or an out-of-process WASM sandbox with CPU/memory limits.

Tool policy & MCP tool calls

S-04HighThe one governed tool-call path doesn't call tools

Metering & enrichment

  • Throughput ceiling: 500 calls per 60 s run is about 30k calls/hour. A busy deployment builds an enrichment backlog, and budgets lag further.
  • N+1: one SELECT feature_tag per call and one cache read per call inside the loop (metering.py:139-149).
  • Schedules are intervals, not crontabs (core/celery_app.py, comment "approximate — use celery beat crontab for prod"). Daily jobs (budget sync, ledger snapshots, billing reconciliation, retention) drift and restart their timer whenever beat restarts. The production beat container is four weeks older than the API and worker, so it may schedule task names or arguments the newer worker no longer has.
  • Pricing coverage: 28 pricing rows in prod. When gateway calculate_cost returns None (unpriced model), finalize writes a ProviderCall with tokens and a NULL cost. Ironically, that's the only case where gateway spend can later reach budget counters: through enrichment, once a price is added, and then attributed to the wrong period (B-07). Resolved: unpriced calls listed; new pricing prices earlier calls, in the call's period

  • False positives: verify_snapshot rebuilds totals from live provider_calls (services/ledger.py:204). Late enrichment (cost NULL → value), late OTLP traces for that day, or retention deletes all change the totals, so honest data reads as "tampered".

  • Key custody: the HMAC key lives in the same DB, encrypted only if LEDGER_MASTER_KEY is set, otherwise plaintext (52-56). Decrypt failure silently returns the ciphertext as the key (63-66).
  • func.date(created_at) == d uses the DB session's timezone and defeats indexes.
Fix: per-row hash chain at insert time (each ProviderCall hashes its canonical fields + previous hash per workspace), daily Merkle root over the chain, root anchored externally (S3 Object Lock / transparency log). Verify the chain, not live aggregates. Treat cost enrichment as an append-only adjustment event.
