Eight features, audited in parallel: backend, frontend and cohesion

Eight independent code-review agents each took one major feature from the feature catalog and audited its backend (endpoints, authorization, validation, correctness, efficiency), its frontend (components, API calls, filters, pagination, states) and its real connections to the other features. They produced 213 findings with file:line evidence. I spot-checked 18 of the most severe claims directly against the source; all 18 held. This pass is additive to passes 1–3: agents were told the earlier findings and focused on new ones.

Bottom line. The newest and most serious class of problems is tenant isolation and identity, not features:
  • An org admin of any tenant can take over any account, including the platform admin (A-01, A-02).
  • Any org admin can dump the entire multi-tenant database to their own S3 bucket (P-02 / I-03).
  • Anyone who knows a workspace UUID can inject runs (I-01), and pipeline events can modify other tenants' runs (I-02).
  • Every default Compose install ships a known platform-admin password (P-01).
Combined with pass 2 (guardrail exec() RCE, route secret exfiltration), the platform should not be offered as multi-tenant until these are closed. Feature-wise, the pattern from passes 1–3 is confirmed at depth: wide CRUD, decorative enforcement, silent UI failures, and parallel systems for the same concept.

Remediation roadmap

Week 0–1 · Stop-ship security

  1. Separate identity from membership: invitations need acceptance, org admins can't edit global users, IdP links only inside the tenant (A-01, A-02, A-03).
  2. Gate the default seed behind dev only; set ENVIRONMENT=production in Helm and fail closed (P-01, P-04, P-14).
  3. Backups platform-admin only with encrypted, write-only secrets (P-02/I-03, P-03).
  4. Authenticate or remove the webhook ingest; add ownership checks in the pipeline (I-01, I-02).
  5. From pass 2: disable guardrail exec(); validate route base_url/env var.
  6. Encrypt all stored secrets and redact them from responses (S-03, S-04, G-05, B-09, F-15).

Weeks 2–3 · Sessions, authorization, audit

  1. Session revocation on logout, deactivation and switch; re-check membership; short TTL plus a BFF (A-04, A-07, P-06, P-07).
  2. Login rate limit and lockout; OIDC nonce/PKCE with Redis state (A-06, A-11, S-14).
  3. One role matrix; admin dependencies on all mutations; enforce key scopes (G-17, B-22, S-05).
  4. Audit events with actor, inside the transaction, covering every mutation (S-02, S-16, A-08, G-10).

Weeks 3–5 · Fix what's broken

  1. Fix all the 404/500 endpoints and the crashing workers (B-01, B-04, B-05, B-06, B-12, G-07, G-08, F-07, S-01).
  2. Replace .catch(() => {}) with per-card error states; add error.tsx; a contract test that every lib/api.ts path exists in OpenAPI.
  3. Pipeline savepoints, retry, DLQ, field limits; enrichment starvation fix (I-05, I-06, I-14, F-06).
  4. Explorer and Runs filter fixes; unified outcomes (O-01, O-02, O-03, O-11).

Weeks 5–8 · Cohesion

  1. One billable-cost definition and one observability query service backed by rollups (F-10, O-06, O-16).
  2. One budget primitive (scope: workspace/workflow/key/model/group) enforced in preflight (G-01, G-02, pass 2 B-01).
  3. One ToolPolicy engine for check, MCP, dry run and gateway (S-06, S-07).
  4. Workflow = feature_tag with run attribution on GatewayRequest and GuardrailEvent (B-11, G-19, I-07).
  5. Close the improve loop through Flywheel; Playground, evals and judge through the gateway (B-10, B-20).
  6. Generate Postman from OpenAPI; fix docs and onboarding snippets (all agents).

Each reported independently; there was no cross-agent coordination, so a few findings appear under two features (e.g. backups P-02 and I-03; enrichment starvation F-06 and I-06).
