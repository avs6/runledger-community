Technical due diligence · Pass 2 · Code level

The gateway, the budget engine and governance, line by line

This pass traces each request and each dollar through the code, then checks the most important claims against the running home-lab deployment. The main result is that the gateway's request path is real and fairly sophisticated, but the policy, budget and governance layers around it contain silent failure modes, two critical security issues, and several features that are stubs behind complete-looking UIs.

Scope: apps/api/runledger_api (routers, services, workers), apps/gateway-rs/src/main.rs, sidecars. Verification: read-only SQL and log inspection on 192.168.1.72; two read-only probe scripts run inside the API container and then deleted. Confidence tags: prod-verified (reproduced on the live system), code-verified (unambiguous in source), inferred (strong reading, not executed).

Build features that are stubs or dry runs behind full UIs
Top risks in one paragraph. Any holder of any workspace API key can create a "custom" guardrail whose Python runs via exec() inside the API process, behind a regex denylist that can be bypassed (G-01). Any org admin can point a route at an external host and choose which API-process environment variable is sent as the Bearer token, for example ADMIN_SECRET or DATABASE_URL (G-02). Streamed gateway responses, which are most agent traffic, produce no run, no cost and no budget impact: the only record of them is a runtime event that the API rejects with HTTP 400 every time (G-03, prod-verified). Budget counters are fed only by a background enrichment job that skips gateway calls, and nothing in the gateway reads them anyway (B-01–B-04).

Gateway · request lifecycle (as implemented)

Auth, IP ACL, required metadata, tags

G-18MediumIP ACL is spoofable and crashes for OIDC callers

gateway-rs takes client_ip from the first X-Forwarded-For value (main.rs:483) with no trusted-proxy list, so any client can claim an allow-listed IP. In preflight, evaluate_ip_acl(..., api_key_id=api_key.id, ...) (gateway_runtime.py:211) dereferences api_key, which is None for OIDC-authenticated callers, so OIDC callers sending XFF get a 500. The ACL also keys on metadata["team"], a legacy concept, in the hot path.

Fix: use the socket peer address unless the peer is a configured trusted proxy (Caddy); guard api_key; replace team_name with access group.

Required-metadata enforcement supports both modes: warn (appended to decision_reason as metadata_warn:) and reject (settings.required_metadata_mode == "reject" raises, services/security.py:786; exposed on the Security page). Note it's evaluated after the IP ACL but before the cache, so it's one of the few controls cache hits don't skip. Tags are merged from body metadata and the X-RunLedger-Tags header, then resolved. That's reasonable.

Exact cache & semantic cache

G-05HighCache hits bypass guardrails and controls

The exact-cache check (gateway_runtime.py:231-267) and semantic-cache check (269-314) both return before pre-call guardrails (349), cost caps and RPM. A prompt that a guardrail added later would block is still answered from cache. A rate-limited end user keeps getting answers, and a guardrail-modify (PII redaction) never runs on cached paths. Cache hits also skip run recording: they create a GatewayRequest row only, so cache-hit traffic is invisible in Runs and in savings attribution by workflow.

Fix: order = auth → ACL → guardrails(pre) → rate/budget → cache → route. Record a zero-cost run with cache_hit=true so savings are attributable.
G-06HighSemantic cache leaks responses across users in a workspace

_scope() sets security_scope: "" and knowledge_version: "" with a comment "Placeholders until … wired (P5+)" (services/semantic_cache.py:44-52). Any two callers in the same workspace with the same model and system prompt share answers at ≥0.95 cosine similarity. User A's answer containing their account data can be served to user B. The exact cache has the same problem: workspace-scoped, not key- or user-scoped.

Fix: include api_key_id (default) or end_user_id in the scope. Make "shared" an explicit per-route opt-in. Never semantic-cache responses containing tool calls.
G-07HighExact cache key ignores request parameters

make_cache_key(model, messages) hashes only model + messages (services/gateway.py:111). Requests with different tools, tool_choice, response_format (JSON-schema vs text), temperature, seed or max_tokens collide. A caller asking for JSON can receive a cached prose answer, and an agent offered different tools can receive a tool call for a tool it doesn't have. Caching is on by default (body.get("cache")…unwrap_or(true), main.rs:586-589).

Fix: hash the canonical provider-bound body (minus stream and user). Skip caching when temperature>0 unless explicitly requested. Default cache=false.
G-19MediumLookup and store use different keys

Lookup hashes the original messages (233); finalize stores under prepared_messages, which are post-compiler and post-guardrail-modify (657). With the context compiler or a modify guardrail enabled, the exact cache never hits, yet the UI reports it as enabled.

Context compiler & intelligent router

G-09HighRaw prompts leave the trust boundary before guardrails

The compiler (316-328) and router (333-347) run before pre-call guardrails (349), so unredacted content (PII, secrets) is sent to two sidecars, and to whatever model the router uses. PII redaction of forwarded messages happens only when stream=True (504-508); non-streaming requests to a route with pii_redaction_enabled are forwarded unredacted.

Fix: run guardrails and redaction first. Apply redact_messages regardless of streaming.
G-04HighIntelligent routing is a silent no-op with a 25-second tax

ROUTER_SVC_URL defaults to gateway-rs, which registers only three routes (main.rs:416-420). A live probe returns POST :8210/classify → 404. classify() catches everything and returns None. Its timeout is 25 s (ROUTER_TIMEOUT_SECONDS), and the compiler's is also 25 s. A slow sidecar can add up to 50 s before the first byte with no visible error. When classification fails, routing_config.on_failure can still rewrite the alias, so a misconfigured tier map silently changes models.

Fix: implement /classify in Rust (or deploy router-svc). Sidecar budgets of about 150–300 ms. Emit gateway.enforcement.applied{action:"router_fail_open"} and show a counter on the Gateway page.

Guardrails in the request path

What works: pre-call evaluation with block (451) and modify; post-call evaluation in finalize; per-key guardrail sets; access-group guardrail profiles; workspace bypass flag; a GuardrailEvent row per rule evaluation.

G-08HighModify-mode rewrites the wrong messages

pre_texts includes only messages with truthy content (359), but the rewrite loop indexes messages by position (376-381). In any conversation containing an assistant tool-call message (content null) or an empty message, redacted text i lands on message i of the full list. The wrong turn gets overwritten and the PII stays in the original turn. Inside the engine, skip_system_messages rebuilds texts from the original messages, discarding earlier rules' modifications (guardrails.py:1002-1009).

Fix: carry (message_index, text) pairs through the engine; apply by index; handle multimodal content arrays.
G-10HighPost-call block loses the spend

When a post-call or "during" guardrail blocks, finalize raises 451 before _record_canonical_gateway_run (615-651 vs 677). The provider has already charged for the tokens, but no run, ProviderCall or cost is written. Post-call checks inspect only choices[0].message.content, not tool_calls[].function.arguments, which are a primary data-exfiltration channel for agents. The "during_call" phase is evaluated after the fact over input+output, so it's misnamed and doubles the evaluation cost.

Fix: record the run with status=blocked_post_call and cost, then return 451. Evaluate tool-call arguments.

Route selection

choose_route_for_alias (services/gateway.py:396-516) layers routing groups (tag match), required/excluded tags, region preference, 24-hour region-latency ranking, group strategies (latency_optimized, round_robin), then the policy engine, then priority. It's a capable design, with some defects:

  • "Round robin" is random.choice (495): not round-robin, and uneven at low volume.
  • Group latency_optimized averages all-time latency (no time window, 467-478). A route that was slow months ago stays penalized.
  • Legacy TeamModel fallback in the hot path (420-443) builds a transient GatewayRoute with an endpoint_url attribute the executor never reads (it reads base_url). Preflight then calls select_routes() for the same alias, gets nothing, and continues, so team-model aliases always end in 502. It's dead weight and should be deleted.
  • Duplicate work: preflight calls choose_route_for_alias for the primary alias, then again inside the step loop for the same alias, plus select_routes again (383, 458, 466). See hot-path cost.

Fallback, retries, error semantics

G-11HighError-triggered fallbacks can't fire

Policy fallbacks carry required_error_triggers such as content_policy or context_window. In Rust, a step with required triggers is skipped unless a previous failure produced that trigger (main.rs:524-531). But providers return those errors as 400/413, which are non-transient, and the loop returns 502 immediately on any non-transient failure (622-632). The trigger is classified and then thrown away, so the "fallback on content filter / context overflow" feature never fires.

Fix: on non-transient failure, continue to the next step whose triggers match; return only when none match. Return the provider's status code (400/413) instead of 502.
  • Retries with no backoff or jitter (533-535): a 429 is retried immediately up to retry_count times, which makes rate limiting worse. Retry-After is ignored.
  • Cooldown is set on transient failures via /internal/route-result, with one synchronous DB commit per attempt (gateway_runtime.py:758-778). Even success commits a row update on every request.
  • Upstream error bodies are echoed to clients verbatim (upstream_body), which can leak provider account details.

B-06HighBudget tiers are applied to the wrong scope

The API key carries budget_tier_id (passed into the preflight response), but check_cost_cap ignores it and picks BudgetTier … ORDER BY is_default DESC LIMIT 1 for the workspace. It compares that against one route's spend, not the key's spend, and the whole block runs only if the route has its own cap. A per-key tier of $50/month never blocks a key that spreads across uncapped routes.

G-13MediumBreaches look like outages

Cap and RPM exceptions are caught with except HTTPException: continue (gateway_runtime.py:502). If every route is capped, the client gets 502 No runnable gateway routes remained: no 429, no X-Cost-Cap-Reason, no Retry-After. Clients can't tell a budget stop from an outage, and retry loops make it worse.

G-14MediumRPM limiter semantics

A fixed one-minute window (the docstring says "sliding"), with non-atomic INCR then EXPIRE. It's evaluated for every candidate route in the ordered list during preflight, so fallback routes accrue hits for requests they never served. It runs only when X-RunLedger-End-User-Id is present, so omitting the header bypasses it. It fails open on Redis error.

G-16 · G-17MediumLegacy concepts and fake prices in the hot path

Project and TeamModel budget checks still execute on every capped route (4 extra queries), contradicting AGENTS.md's legacy-cleanup rule. The project is chosen arbitrarily (LIMIT 1 on any active project), so one project's budget can block unrelated traffic. Unknown models are priced at $0.50/$1.50 per 1M, so Ollama traffic consumes cost caps although its real cost is $0.

G-20MediumPer-request overrides mutate shared ORM state

Secrets in transit: for direct mode, the provider API key is read from the API's environment and returned to Rust inside the preflight JSON (request_headers) on every request. Any request/response logging on that internal hop, including the SQL-echo dev mode, puts provider keys in logs. Prefer Rust reading its own secrets by reference.

Streaming & finalize

G-03CriticalStreamed requests are not metered, recorded or guarded

On ProviderSuccess::Stream, Rust emits one gateway.request.completed event (no token counts) and returns the stream (main.rs:536-560). It never calls finalize, so streaming requests get no AgentRun, no Span, no ProviderCall, no cost, no post-call guardrails, no cache store. The only trace is the event, and that fails too: uuid_like() returns "gw_" + hex (1168-1170), which isn't a UUID, so the API's event endpoint returns 400. Production gateway-rs logs show 12 "runtime event emit failed … 400 Bad Request" since the last restart, and the same 400 hits every rejected (all-routes-failed) request. Streaming is the default mode for coding agents and chat UIs, so the gateway's FinOps view systematically misses its largest traffic class.

Fix: tee the SSE stream in Rust, parse the final usage chunk (send stream_options.include_usage=true upstream), and call finalize asynchronously after the stream ends with accumulated content. Use real UUIDv4 request IDs. Add a contract test that posts a Rust-shaped event to the API.

Mirror / shadow traffic

G-12HighShadow calls block the user response

After a successful finalize, Rust awaits call_mirror before returning the 200 (main.rs:600-613). /internal/mirror performs the shadow provider call synchronously (gateway_runtime.py:812-828). For sampled requests the user waits for both models. For unsampled requests there's still an extra round trip. Mirrored prompts also skip guardrails and redaction, and the mirror's spend is recorded without cost, so it's invisible to budgets.

Fix: tokio::spawn the mirror, sample in Rust before calling, and record shadow cost under a shadow flag.

Runtime events & observability of the gateway itself

  • G-15 · overhead metric is fabricated: Rust sends total_wall_ms: Some(latency_ms) (main.rs:579-580), so finalize computes gateway_overhead_ms = max(total − latency, 0) = 0 for every request. Any dashboard tile showing gateway overhead is showing a constant.
  • Signature: HMAC over workspace_id.timestamp.body with a ±5 min window (services/gateway_runtime.py:32-54), with no nonce, so events can be replayed within the window. Duplicates are de-duplicated only by request_id, which currently fails to parse anyway.
  • Batch semantics: one bad event raises 400 for the whole batch (270-279).

Budget enforcement · end-to-end trace

Budget findings

B-01CriticalNo inline enforcement

Call sites of check_budgets: routers/budgets.py:826 (the /budgets/check endpoint) and services/policies.py:269 (/policies/check). The gateway preflight (gateway_runtime.py:198-596) has no reference. check_model_budgets and incr_model_budget_spend have no call sites at all. docs/finops/budgets.mdx says "Inline (gateway) — blocking, enforced before the provider call", which is false.

B-02HighThe counter feed skips gateway traffic

Counters are incremented only inside _run_cost_enrichment, which selects ProviderCall.cost_usd IS NULL AND input_tokens IS NOT NULL (workers/metering.py:111-118). Gateway finalize writes ProviderCalls with cost_usd already computed (gateway_runtime.py:124-141), so enrichment never sees them. The same applies to any SDK or OTLP span that reports its own cost (llm.cost.total). Until the daily sync runs, gateway spend counts as $0 against every budget.

B-03 · B-04HighScope handling is inconsistent between increment and sync

Increment: _matching_budgets(budgets, end_user_id=…, feature_tag=…). api_key, access_group, app and provider_profile are never passed, so those budgets never accrue (metering.py:144-148). Sync: filters only for end_user and api_key. For every other scope it sums all workspace spend, with a comment "feature_tag is on agent_runs … skip for now" (workers/budgets.py:238-259). A $20 feature_tag budget is therefore reset nightly to, say, the $4,000 workspace total and shows as 20,000% consumed. Through /policies/check it then blocks or downgrades every request for that feature. Access-group budgets, which the docs call "first-class budget scopes", are wrong in both directions. Partly resolved: increment path fixed for all scopes; nightly sync overwrite (I-08) still open

B-05HighCounters aren't durable

Redis runs with --maxmemory 256mb --maxmemory-policy allkeys-lru --appendonly ${…:-no} (docker-compose.yml:55). Under memory pressure from response caches, rate-limit keys or Celery, LRU may evict rl:budget:*:spend:*, resetting spend to 0 until the next daily sync. A Redis restart without AOF does the same.

Fix: use Postgres as the source of truth (a budget_spend table updated transactionally in finalize/ingest), Redis as a write-through cache with volatile-lru, and keep budget keys without TTL eviction.
B-07 · B-08MediumTime attribution and stalls

Counters use datetime.now() at enrichment time (services/budgets.py:72), so a call made at 23:59 and enriched at 00:01 lands in the next day, and backfilled pricing dumps historic spend into today. Enrichment orders by created_at and LIMIT 500; unpriced calls are skipped but stay NULL, so once 500 unpriced calls exist, every run re-selects the same 500 and enrichment stops for all newer calls.

B-09MediumRunaway protection doesn't protect

Every 5 minutes the worker finds runs with status='running' for >2 minutes with >20 calls or a >100k-token call and sets status='cancelled' (workers/budgets.py:81-120). Gateway and OTLP runs are created as succeeded, so they never qualify. Nothing in the gateway checks run status, so a "cancelled" run keeps spending. It's notification-only behavior presented as a kill switch.

Governance & security

Custom guardrail sandbox

S-01CriticalRemote code execution in the API process

execute_custom_logic compiles and exec()s user-supplied rule.logic (services/guardrails.py:164-166). Its only protection is a regex denylist (100-129) for words like import, __class__, getattr, os.. The sandbox globals expose the real re module (97). Module objects carry references back to builtins and other modules, and string-built attribute names defeat word-boundary regexes. Denylist sandboxes of this kind are a well-known, repeatedly broken pattern. Also:

  • timeout_ms is accepted but never enforced, so while True: pass blocks the async event loop and stalls every request on that worker.
  • POST /guardrails depends only on WorkspaceDep (any valid API key, including SDK and ingest keys embedded in agents), while update requires workspace admin (routers/guardrails.py:123-131 vs 245-253). Resolved: POST /guardrails requires workspace admin
  • Exceptions fail open (return allow), so a broken rule silently disables itself.

Impact: code runs with the API's environment (DATABASE_URL, SECRET_KEY, ADMIN_SECRET, provider keys), so it's a cross-tenant compromise.

Fix (immediately): disable custom/template logic execution behind a feature flag defaulting off; require workspace admin on create. Then: replace with a non-Turing-complete policy language (CEL, JSONLogic, Rego/OPA) or an out-of-process WASM sandbox with CPU/memory limits.

Tool policy & MCP tool calls

S-04HighThe one governed tool-call path doesn't call tools

POST /mcp-registry/tools/call runs govern_and_filter_tool_call (tool policies, guardrails, plugin hooks), then writes an McpToolCall with status="success" and result=None. It never contacts the MCP server (mcp_registry.py:248-310). For require_approval, it returns approval_id = "appr_" + hex[:12] (plugin_runner.py:~201) without creating an Approval row, so the ID can't be approved, denied or listed. Scope-aware policy matching uses access_group_id / api_key_id from the request body, so the caller can choose the identity that avoids a policy. The endpoint requires workspace admin, so agents can't use it anyway.

Fix: make this a real MCP proxy (stdio/HTTP client per server, connection pool) with identity derived from the authenticated key; create real Approval rows and a resumable call state. Apply the same governance in gateway preflight (filter tools[]) and finalize (inspect tool_calls).

Approvals & plugins

  • Approvals are created only via POST /approvals (a client asks) and budget-override requests (budgets.py:1329). Approve/deny update state. No runtime path waits on them, so they work as a ticket queue for cooperative clients.
  • Plugins are simulated. execute_plugin_hooks logs executing_plugin_hook and records a PluginExecution with status success. No webhook, code or HTTP call is made (plugin_runner.py:44-55, comment "Simulate plugin hook execution logic / webhook dispatch"). The Plugins page and execution logs therefore show fabricated successes.

RBAC & API key scopes

S-03HighScopes are decorative; most mutations accept any key Resolved: require_workspace_writer on all mutations; scopes read/write/ingest/gateway/mcp enforced

ApiKey.scopes is stored, returned and passed to Rust, but no dependency checks it. WorkspaceDep (any key) is used 240 times. These routers expose create/update/delete with no admin dependency: agents, eval_experiments, evaluations, flywheel, ingest, intelligence, outcomes, playground, policies, prompts, replay, runs, tools, vector_stores, workflows. A leaked ingest key from a customer-facing agent can therefore rewrite prompts (which feed production via GitHub sync), delete workflows, or create guardrails (S-01).

Fix: define scopes (ingest, gateway, read, manage), add require_scope("manage") to all mutations, and default new SDK keys to ingest+gateway.

Route configuration: secret exfiltration and SSRF

S-02CriticalOrg admins can read platform secrets

Route create/update accepts arbitrary base_url and api_key_env_var (gateway_routing.py:252, 351; schema has no validator). At request time, os.getenv(route.api_key_env_var) is placed in Authorization: Bearer … and sent to {base_url}/chat/completions (gateway_shared.py:422-433). A tenant org admin can set base_url=https://attacker.example and api_key_env_var=ADMIN_SECRET (or SECRET_KEY, DATABASE_URL, SMTP_PASSWORD, another tenant's provider key), send one request, and receive the platform secret. base_url can also target internal services (http://runledger-redis:6379, runledger-qdrant, runledger-minio, cloud metadata 169.254.169.254). Passthrough endpoints (_build_passthrough_target_url) have the same lack of egress validation. No private-IP or allow-list checks exist anywhere in the codebase.

Fix: replace api_key_env_var with references to a per-workspace secret store (encrypted provider_credentials table). If env vars must stay, allow-list a prefix (RL_PROVIDER_*). Validate egress URLs (scheme, DNS-resolved IP not private/link-local unless the platform admin enables a "local providers" flag).
S-05MediumInternal endpoints guarded by one shared secret on a LAN-exposed port

/gateway/runtime/internal/* (preflight with any raw key, provider-execute for any route ID, snapshot for any workspace) accept X-Admin-Secret, which is compared with != (not constant-time, core/deps.py:257). The API binds to 192.168.1.72:8201, so anyone on the LAN can reach these endpoints. Separate the internal listener (unix socket or an internal-only port) and use per-service credentials. Partly resolved: constant-time compare; separate listener and per-service credentials still open

Metering & enrichment

  • Throughput ceiling: 500 calls per 60 s run is about 30k calls/hour. A busy deployment builds an enrichment backlog, and budgets lag further.
  • N+1: one SELECT feature_tag per call and one cache read per call inside the loop (metering.py:139-149).
  • Schedules are intervals, not crontabs (core/celery_app.py, comment "approximate — use celery beat crontab for prod"). Daily jobs (budget sync, ledger snapshots, billing reconciliation, retention) drift and restart their timer whenever beat restarts. The production beat container is four weeks older than the API and worker, so it may schedule task names or arguments the newer worker no longer has.
  • Pricing coverage: 28 pricing rows in prod. When gateway calculate_cost returns None (unpriced model), finalize writes a ProviderCall with tokens and a NULL cost. Ironically, that's the only case where gateway spend can later reach budget counters: through enrichment, once a price is added, and then attributed to the wrong period (B-07).

Ledger

M-02 · M-03MediumTamper evidence is unreliable in both directions
  • False positives: verify_snapshot rebuilds totals from live provider_calls (services/ledger.py:204). Late enrichment (cost NULL → value), late OTLP traces for that day, or retention deletes all change the totals, so honest data reads as "tampered".
  • False negatives: snapshots hold only total cost, call count and per-model cost. Moving cost between users, keys or workspaces (chargeback manipulation) while preserving per-model totals goes undetected.
  • Key custody: the HMAC key lives in the same DB, encrypted only if LEDGER_MASTER_KEY is set, otherwise plaintext (52-56). Decrypt failure silently returns the ciphertext as the key (63-66).
  • func.date(created_at) == d uses the DB session's timezone and defeats indexes.
Fix: per-row hash chain at insert time (each ProviderCall hashes its canonical fields + previous hash per workspace), daily Merkle root over the chain, root anchored externally (S3 Object Lock / transparency log). Verify the chain, not live aggregates. Treat cost enrichment as an append-only adjustment event.

OTLP ingest

M-01HighEvery trace becomes a run

synthesize_canonical_events emits run_start for any trace with a root span (services/otlp_parse.py:640-679). The parser recognizes GenAI/OpenInference attributes for provider calls (142-205) but doesn't gate run creation on them. Production: 253,163 OTLP runs with zero provider calls, dominated by Codex internal spans (fs.get_metadata 396k, receiving 322k). Each run also stores the full resource_attributes map, and otlp_spans_raw keeps every raw span (1.97M rows, 1.7 GB) with no retention policy configured.

Fix: create a run only if the trace contains an LLM/agent span (or matches a configured source profile). Store raw spans for N days only. Dedupe resource attributes into a resources table keyed by hash.
