Review burn-down: parallel strategy

How to finish every open item in docs/review/runledger-review.html and add a round of UI/UX "good to have" improvements, using many agents at once without them colliding with each other or with other sessions. Snapshot taken 2026-11-22.

ID collision: the code-deep register reuses prefixes (its B- = budget, G- = gateway, S- = security) that mean something else in the feature register. In this plan, code-deep items are written cd:B-05 and so on. Agents must quote the section as well as the ID when reporting.

Ground rules for every agent

Isolation

One stream = one worktree = one branch (review/<stream>), cut from the review/base branch made in Wave 0. Never work in the main checkout; other sessions use it.

File ownership

Each stream owns the files in the ownership table. To change another stream's file, keep the edit small and additive, and list it under "cross-stream edits" in the PR body.

Migrations

At most one Alembic revision per stream, named <stream>_<slug>. The integrator re-points down_revision at merge time, so the chain stays linear.

Single writer for the review

Only the Wave 3 integrator edits runledger-review.html. Streams list the resolved IDs (with their section) in the PR body.

Done bar (AGENTS.md)

Backend → UI → CRUD → docs → scripts (with asserts) → examples. Postman is skipped (the project has none). Ruff, mypy, pytest, tsc and eslint must be clean.

Environments

Unit tests in the worktree only. The one Docker stack (ports 8201/3201) belongs to the integrator. Never touch the X230 (production). No commits outside the stream's branch.

Waves at a glance

Wave 0 · serial

Land and de-conflict

Commit current work. Split the three hot files. Delete posture sprawl. Build shared UI primitives. 1–2 agents.
Wave 1 · parallel

Nine domain streams

Each fixes every finding in its area, back end to UI, and adopts the new primitives on its own pages. 9 agents.
Wave 2 · parallel

UX enhancements

Navigation redesign, merging duplicate pages, a11y, and the good-to-have features. 3–4 agents.
Wave 3 · serial

Integrate and close out

Merge, run E2E on Docker, consolidate docs and examples, tag the review. 1 agent.

Wave 2 UX & usability (after Wave 1 merges)

W2-A · Information architecture

Six areas (Workflows · Runs · Gateway · Governance · FinOps · Admin) with tabs; nav entries for orphaned pages; merge duplicates (Runs/Sessions/Explorer, Model Usage/Scorecards/Engineering, MCP/MCP Registry, dataset views, Breakdown/Overview, AI Hub/Profiles/Routes); retire legacy surfaces and their hot-path residue (fc-legacy, ui-nav, ui-fixes #7 #11 #12, tr-gui IA). Breadcrumbs and redirects that keep the tab.

W2-B · Accessibility & responsiveness

jsx-a11y becomes an error; aria labels everywhere; focus order, keyboard reachability and contrast tokens; mobile layouts for tables; dark-mode parity; a WCAG 2.1 AA checklist and a VPAT draft (tr-gui a11y, ui-matrix).

W2-C · Power-user features ENH

⌘K command palette and global search (runs, workflows, keys, routes); keyboard shortcuts with a cheat sheet; saved views and pinned filters; recent items; bulk actions; relative/absolute time toggle; density toggle; copy-ID buttons; undo toasts instead of confirm for reversible actions.

W2-D · First-run & guidance ENH

Onboarding checklist (connect a provider, send the first request, set a budget, add a policy); helpful empty states with CTAs and snippets; inline "what is this" help linking to docs; real API Explorer (Redoc) and Design System hidden from customer builds (ui-fixes #9 #10); in-app notification centre for alerts and approvals.

Wave 2 backend needs (a user-preferences API for saved views, density and pins, and a search endpoint) are owned by W2-C.

Wave 3 Integration & close-out (one agent)

  • Merge streams into review/integration in this order: A → I → D → B → C → F → E → G → H, then Wave 2. Re-chain migrations at each merge and run the full test suite after each one.
  • Rebuild the local Docker stack; run verify_api_health.py, every scripts/ E2E, and the Playwright smoke suite.
  • Delivery (tr-delivery, A-23, G-27, top): docs describe real behaviour (budgets, architecture, latency); examples consolidated to about 25 journeys with no numbering collisions; scripts assert enforcement (budget blocks, tool policy blocks, routing tier); repo hygiene (scratch/, root main.py, apps/api;C, version drift, TODO_ITEMS).
  • Tag every resolved row in runledger-review.html (single writer), re-run the tag-balance check, and add a final status banner.
  • Open one PR per wave, or one integration PR, as the user prefers. Never deploy to the X230 unless asked.

Kick-off prompt for each stream session

You are stream W1-<X> (<name>) of the RunLedger review burn-down.
Read docs/review/parallel-strategy.html (your stream card and the ownership table) and AGENTS.md.
Work only in your worktree on branch review/<stream>, cut from review/base.
1. For every ID in your card, read its row in docs/review/runledger-review.html (match the section too: cd:* means the code-deep register).
2. Fix each one to the AGENTS.md done bar: backend, UI, CRUD, docs, scripts with asserts, examples. No Postman.
3. Adopt DataTable / ConfirmDialog / AsyncCard / routes.ts on your own pages; add aria-labels and URL-synced filters.
4. Build the ENH items in your card.
5. Edit only files you own; any small edit outside them goes under "cross-stream edits" in your summary. At most one Alembic revision, named <stream>_<slug>.
6. Do NOT edit runledger-review.html, run Docker, deploy, or touch other branches.
7. Before finishing: ruff, mypy, pytest, tsc and eslint clean. Commit on your branch. Report: resolved IDs (with section), partial IDs with what's left, cross-stream edits, migration name.

Risks & mitigations

RiskMitigation
Uncommitted work missing from worktreesStep 0.1 commits and merges first; nobody starts Wave 1 before review/base exists.
Alembic multiple headsOne revision per stream; the integrator re-chains. CI runs alembic heads and fails on more than one.
Merge conflicts in shared filesWave 0 splits; append-only registries; a fixed merge order; small cross-stream edits declared up front.
Two streams "fixing" one finding differentlyEach ID is assigned to exactly one stream above; anything unassigned goes to the integrator, not whoever finds it.
Decorative features creeping back in (AGENTS.md)Every control must have a runtime enforcement path and a script that asserts it; otherwise hide it or remove it.
Things only the user can doPyPI/npm accounts (I-28), production deploys, secrets for production: listed in the integrator's final report.
