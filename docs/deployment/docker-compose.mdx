Docker Compose is the fastest way to run RunLedger. `docker compose up -d` brings up the whole stack:
control plane, gateway, workers, optimization services, OTel Collector, stores and the local TLS proxy.
Only the bundled Kafka broker is optional (the `streaming` profile).

## Prerequisites

- Docker + Docker Compose
- Git

## Start the stack

```bash
git clone https://github.com/avs6/runledger-community
cd runledger-community
cp .env.example .env
# Fill in SECRET_KEY, ADMIN_SECRET, REDIS_PASSWORD, POSTGRES_PASSWORD and
# RUNLEDGER_BACKUP_SECRET_ACCESS_KEY, each with a value like:
python -c "import secrets; print(secrets.token_urlsafe(32))"

docker compose up -d                          # full stack
docker compose --profile streaming up -d      # also start Redpanda for Kafka export
```

`ENVIRONMENT` defaults to `production`: the API refuses known-default secrets and no account is
seeded. Create the first platform admin once, either in the browser at
`http://localhost:3201/setup` (it asks for `ADMIN_SECRET`) or with the API:

```bash
curl -s -X POST http://localhost:8201/admin/bootstrap \
  -H "X-Admin-Secret: $ADMIN_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@example.com","password":"<12+ chars with a letter and a digit>","full_name":"Admin","org_name":"My Org"}'
```

Bootstrap works only while no platform admin exists (409 afterwards). For a local development stack,
set `ENVIRONMENT=development`: the API then seeds a demo admin (`admin@runledger.local` /
`runledger`), which is refused at sign-in in any other environment.

Api, workers and beat run one image (`runledger-api:${RUNLEDGER_TAG}`), so they can't drift onto
different builds. Platform admins can check workers, queues, beat, migrations, backups and versions
on **Platform → System Status** in the dashboard (`GET /system/status`).

| URL | What it is |
|---|---|
| `http://localhost:3201` | Dashboard |
| `http://localhost:8201/reference` | Interactive API reference (Scalar) |
| `http://localhost:8210/gateway` | Rust gateway (OpenAI-compatible) |
| `http://localhost:4318` | OTLP/HTTP receiver (via OTel Collector) |
| `http://localhost:8201/mcp` | Canonical RunLedger MCP endpoint |
| `http://localhost:8206/mcp` | Optimization MCP gateway |

## Profiles

Every service starts by default except:

- `streaming` → `runledger-redpanda` and `runledger-redpanda-console`, the bundled broker for
  [Kafka export](/integrations/kafka-export). Start it with `--profile streaming`, or set
  `COMPOSE_PROFILES=streaming` in `.env` so every `docker compose` command includes it.
  Skip it if you don't export to Kafka or export to your own brokers.
- `deprecated` → retired services kept only for reference; never needed.

## Load demo data (optional)

A fresh install has empty dashboards. To fill the whole cluster with realistic data — multiple orgs
and workspaces, gateway routes, runs, budgets, outcomes, scores, and alerts — run the simulator. It
drives the **REST API** exactly as a client would (no direct database writes):

```bash
# from the repo root, with the stack running
uv run python scripts/full_simulate.py
```

By default it **resets to a blank slate first** (truncates all data), then bootstraps an admin and runs
every scenario under `scripts/scenarios/`. Useful variants:

```bash
uv run python scripts/full_simulate.py --hard-clean   # wipe every volume first (Qdrant, memory, etc.)
uv run python scripts/full_simulate.py --no-clean     # add on top of existing data
uv run python scripts/cleanup.py                      # just reset (truncate + flush Redis)
uv run python scripts/cleanup.py --hard               # full reset: down -v + up
```

Each scenario is a self-contained Python module in `scripts/scenarios/` — copy one to add your own.
Cost enrichment and rollups run on Celery, so give analytics ~60s to populate. The
[Product Tour](/observability/product-tour) shows what each page looks like with data.

<Note>
`full_simulate.py` **truncates existing data by default** so every run is reproducible. Pass `--no-clean`
to keep what's there.
</Note>

## Common commands

A `Makefile` wraps the everyday tasks so you don't memorize the underlying commands:

| Command | Does |
|---|---|
| `make dev` / `make dev-d` | Start the full stack (foreground / detached) |
| `make ps` / `make logs` / `make logs-api` | Status · all logs · API logs (shows the first API key) |
| `make migrate` | Apply database migrations (`alembic upgrade head`) |
| `make simulate` / `make simulate-hard` | Reset + populate the cluster with demo data (`--hard` wipes volumes) |
| `make clean-data` / `make reset` | Truncate data / full `down -v` reset |
| `make build` | Rebuild images from source |
| `make down` / `make down-volumes` | Stop containers / stop **and wipe** the database |

For contributor workflows — hot-reload dev servers, tests, lint, and type-checks — see the
[Makefile](https://github.com/avs6/runledger-community/blob/master/Makefile) and `CONTRIBUTING.md`.

## What comes up

### Control plane

| Component | Host port | Env override | Role |
|---|---|---|---|
| `runledger-web` | 3201 | `WEB_PORT` | Next.js dashboard |
| `runledger-api` | 8201 | `API_PORT` | FastAPI control plane (+ /reference, /mcp) |
| `runledger-gateway-rs` | 8210 | `GATEWAY_RUNTIME_PORT` | Rust gateway (OpenAI-compatible data plane) |
| `runledger-postgres` | 5432 | `POSTGRES_PORT` | System of record |
| `runledger-redis` | 6379 | `REDIS_PORT` | Queue / cache / budget hot-path |
| `runledger-worker` | — | — | Celery worker for the default queue (enrichment, rollups, exports, backups) |
| `runledger-worker-ingest` | — | — | Celery worker for the `ingest` queue only, so event processing never waits behind slow jobs |
| `runledger-beat` | — | — | Celery periodic scheduler |

### Network exposure

Only client-facing ports listen on all interfaces: API (8201), gateway (8210), web (3201), Caddy (3443/8443), MCP gateway (8206) and OTLP (4317/4318). Every other host port below — Postgres, Redis, Qdrant, MinIO, Redpanda, Letta, the optimization microservices and the collector's internal endpoints — is published on `127.0.0.1` only (`RUNLEDGER_INTERNAL_BIND`). Set it to `0.0.0.0` only on a trusted network where another machine must reach them directly.

The optimization microservices also require `X-Internal-Token` (`INTERNAL_SERVICE_TOKEN`, default `ADMIN_SECRET`) on every non-health request, so reaching a port is not enough to read or write workspace data.

### Observability & TLS

| Component | Host port | Role |
|---|---|---|
| `runledger-otel-collector` | 4317 (gRPC) / 4318 (HTTP) | OTLP receiver |
| `runledger-otel-collector` | 13133 / 8888 / 8889 / 55679 | Health, self-metrics, span metrics, zPages |
| `runledger-caddy` | 3443 / 8443 | Local HTTPS reverse proxy (web / API) |

Local LLM runtimes (Ollama / vLLM) stay **external** — point `OLLAMA_BASE_URL` / `VLLM_BASE_URL` at them.
See the [Token Optimization overview](/optimization) for the full service map.

The API exposes `/health/live` plus `/health/ready`, and the optimization sidecars expose
`/health/ready` as a consistent readiness path for local probes and container healthchecks.
For local HTTPS, `runledger-caddy` serves `https://runledger.localhost:3443` and
`https://api.runledger.localhost:8443`.
