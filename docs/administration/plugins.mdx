The **Plugins** route (`/plugins`) is intentionally collapsed. The UI redirects to `/onboarding?section=connections` because plugin discovery and setup are owned by the Onboarding surface.

## Why Plugins Is Collapsed

Plugins started as a standalone admin destination but evolved into a backend-only capability surface. The user-facing discovery and connection management now lives in **Onboarding → Connections**, where it fits naturally into the setup and integration workflow.

## Backend API (Active)

The plugin CRUD API remains active and is consumed by MCP tool governance and builder workflows:

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/plugins` | Install/create a plugin |
| `GET` | `/plugins` | List plugins |
| `GET` | `/plugins/{id}` | Get plugin detail |
| `PUT` | `/plugins/{id}` | Update plugin |
| `DELETE` | `/plugins/{id}` | Uninstall (deactivate) plugin |
| `GET` | `/plugins/{id}/executions` | Plugin execution log |
| `POST` | `/plugins/seed-defaults` | Seed default plugins |

## Ownership Model

- **Onboarding** owns user-facing plugin discovery and connection setup
- **Evaluation studio** consumes plugin connections as tool integrations in builder workflows
- **MCP governance** uses the plugin CRUD backend for tool policy enforcement
- **Platform settings** does not own plugins — they are workspace-scoped, not platform-wide

## Adjacent Relationships

- **Tool Registry & Tool Policies**: plugin hooks are governed by tool policies. When a plugin registers hooks (`on_run_complete`, `on_alert_fired`, etc.), tool policy enforcement determines whether those hooks execute. Plugin CRUD is the registration surface; Tool Policies is the governance surface.
- **Monitoring**: plugin execution logs (`GET /plugins/{id}/executions`) provide an operational audit trail. Alert rules can reference plugin-generated events, and guardrail events may be triggered by plugin hook executions. Monitoring surfaces plugin operational health at the platform level.
- **Evaluation Studio**: evaluation experiments consume plugin-provided tool connections. When an experiment needs external tool access, it resolves through the plugin connection graph registered via this API.

## Lifecycle Notes

- The `/plugins` redirect is a permanent product decision, not a temporary gap
- Backend endpoints are workspace-scoped (Bearer API key auth)
- Plugin execution logs provide audit trail for MCP tool calls
- Seed defaults bootstraps standard integrations during onboarding
- Plugin hooks are subject to tool policy enforcement from the governance layer
