title: "Access Groups"
description: "Workspace-scoped governance groups for member assignment, budgets, and guardrail envelopes."
---

The **Access Groups** page lets workspace admins define reusable governance bundles for a workspace. Each group can carry a budget envelope, guardrail profile, and dashboard filter context, then map users into that policy surface.

## Who Can Manage Access Groups

- Workspace admins can create, edit, deactivate, and manage group membership.
- Org admins and org managers inherit workspace-admin capability for the active workspace.
- Non-admin members can review the dashboard summary, but they cannot mutate groups or membership.

## What Lives Here

- Create and update access groups.
- Deactivate groups that should no longer grant membership.
- Add and remove members.
- Attach budget and guardrail posture to a reusable workspace group.
- Drill directly into the group's scoped budget, billing, and chargeback posture.

## Financial Scope

Access groups are now a real financial scope primitive in the product, not just a visual grouping helper.

- **Budgets** can be created and filtered with `scope_type=access_group`.
- **Billing periods** can be filtered to traffic attributable to access-group members.
- **Chargeback** can report directly on the `access_group` dimension and compare those allocations to matching budgets.

## Observe Investigation

Access groups are now a real Observe investigation dimension too.

- **Analytics Overview** accepts `access_group_id` and narrows the workspace overview to that scoped operator footprint.
- **Runs** and **Run detail** preserve `access_group_id` so investigators stay inside the selected scope while moving from list to execution evidence.
- **Request Flow** and **Request Explorer** both accept `access_group_id`, making it possible to move from the group dashboard into routing causality and request-level debugging without rebuilding filters by hand.

The access-groups dashboard links into `/analytics`, `/runs`, `/request-flow`, `/request-explorer`, `/budgets`, `/billing`, and `/chargeback` with the correct access-group scope pre-applied.

## Gateway and Runtime Integration

- `GET /analytics/access-group-gateway-posture?access_group_id={id}` returns the workspace gateway posture relevant to the access group: route count, active routes, distinct providers, routing policies, guardrail count and active guardrails, and passthrough endpoint count. The response also surfaces the group's `guardrail_profile` for quick reference.
- The Access Groups page links directly to Gateway, Provider Profiles, Rate Limits, and Guardrails for workspace-level runtime context.
- Access groups carry a `guardrail_profile` field that the guardrails engine resolves at runtime, making the group a first-class runtime governance scope.

## Product Fit

Access Groups are a workspace-scoped governance primitive. They should not become a parallel organization model or a replacement for workspaces. Use them to shape access and policy inside a workspace, not to model legacy teams or projects.
