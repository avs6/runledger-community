The **Users** page is where admins manage people and access inside an organization. Organization lifecycle lives separately on the **Organizations** page. Sign-in, sessions, and password rules are described in [Sign-in & Sessions](/administration/authentication).

## Who Can Access Users

- Platform admins can manage users across the installation.
- Org admins and org managers can manage users and memberships inside their organization.
- Workspace admins do not see Users. They manage workspace-level controls such as API Keys, Budgets, Approvals, and Audit Log for their active workspace.
- Members do not see Users.

## User Lifecycle

- **Create:** enter an email and optional name. Leave the password empty to generate one. The temporary password is shown **once** and must be changed at first sign-in. Tick **Mark email verified** when SMTP is not configured. Otherwise a verification email is sent.
- **Invite to org:** inviting an email that already has an account creates a pending invitation. The person accepts it from **Account → Invitations**. Until then the membership shows as **Invited** and grants no access.
- **Edit identity:** display name, password, active and verified flags. These controls are enabled only when your org exclusively owns the account. Shared accounts (members of other orgs, or platform admins) show identity controls read-only. You can still change their role, suspend them, or remove them.
- **Deactivate:** this asks for confirmation. Deactivation revokes all of the user's sessions immediately. You cannot deactivate yourself.
- **Sign out everywhere:** this revokes every live dashboard session of the user (`POST /users/{id}/sessions/revoke`).
- **Remove from org or workspace:** this revokes the user's sessions in the affected workspaces.

The user list is paginated (`GET /users/all?limit=&offset=`, at most 500 per page).

## Role Model

| Role | Scope | Typical Access |
|---|---|---|
| Platform Admin | Platform | Organizations, Settings, all org/workspace views |
| Org Admin | Organization | Everything in the org, including granting `org_admin` |
| Org Manager | Organization | Users and workspaces; can manage every role below `org_admin` |
| Org Billing Admin | Organization | Read access to every workspace, plus **Billing** and **Chargeback** (periods, reconciliation, exports, reports). Read-only unless they also hold a writable workspace role |
| Org Auditor | Organization | Read access to every workspace, plus the **Audit Log** and **Audit Pack** for each workspace and the org. Read-only unless they also hold a writable workspace role |
| Workspace Admin | Workspace | Everything below, plus governance config: API Keys, Budgets, Guardrails, Tool Policies, Approvals, Audit Log, routing/flywheel settings, prompt GitHub sync |
| Workspace Editor / Contributor / Member | Workspace | Create and change workspace content: prompts, agents, workflows, evaluations, datasets, experiments, outcomes, vector stores, tool registry, playground |
| Viewer | Workspace | Read-only. Write calls return `403 Your role in this workspace is read-only` |

Use workspace membership to decide what a user can do inside each workspace. A user can be admin in one workspace and a viewer in another. Adding someone to a workspace requires them to be an active member of the org. The API enforces these roles on every request (see [Sign-in & Sessions](/administration/authentication#roles-and-write-access)); the dashboard hides actions a role cannot take.

## Audit

Every user and membership change is written to the audit log with the org's `tenant_id`. This includes create, identity edit, role change, status change, invite, accept or decline, removal, and session revocation. **Org → Audit Log** shows org-level and workspace-level events together (`GET /org/audit-log?limit=&offset=`, for org admins and org auditors).

## User Detail — Governance Footprint

Each user's detail page shows their governance activity alongside financial exposure:

- **Approval count and recent approvals:** how many governance requests this user submitted and their latest decisions.
- **Audit event count and recent events:** how many audit trail entries this user generated.
- **Cross-links:** jump directly to Approvals (filtered by requester), Audit Log (filtered by actor), or Governance Pack (scoped to user) from the user detail page.

The governance endpoint `GET /users/{user_id}/governance` returns the summary programmatically.
